# lsapctl Runtime Contract

`lsapctl` is the only lifecycle manager inside generated Linux packages.

Dagger generates runtime inputs only:

```text
rendered/lsapctl-runtime.json
rendered/docker-compose.yml
rendered/install-config.json
rendered/build-lock.json
rendered/workloads.json
systemd/*.service
components/*
```

Dagger must not generate:

```text
install.sh
start.sh
stop.sh
uninstall.sh
```

## Commands

Recommended command surface:

```bash
lsapctl doctor --manifest rendered/lsapctl-runtime.json
lsapctl install --manifest rendered/lsapctl-runtime.json
lsapctl start --manifest rendered/lsapctl-runtime.json
lsapctl stop --manifest rendered/lsapctl-runtime.json
lsapctl restart --manifest rendered/lsapctl-runtime.json
lsapctl status --manifest rendered/lsapctl-runtime.json
lsapctl uninstall --manifest rendered/lsapctl-runtime.json
```

`install`, `start`, `stop`, `restart`, `status`, and `uninstall` should run environment checks first. `doctor` runs checks only.

Implemented CLI features:

- Cobra-based subcommands, help, and shell completion
- colored and aligned check/status output
- progress spinner for external commands
- interactive install directory prompt
- automatic backup before install
- dynamic sudo re-exec for privileged operations

Shell completion:

```bash
./lsapctl completion bash | sudo tee /etc/bash_completion.d/lsapctl >/dev/null
./lsapctl completion zsh > "${fpath[1]}/_lsapctl"
./lsapctl completion fish > ~/.config/fish/completions/lsapctl.fish
```

Interactive install:

```bash
./lsapctl install --interactive
```

If `--install-dir` is not provided, `lsapctl install` uses this default order:

```text
runtime manifest installDir -> /opt/lsap
```

Before installing, `lsapctl` shows the default install directory and asks the user to confirm or edit it. Use `--yes` for non-interactive installs.

Override target directory:

```bash
./lsapctl install --install-dir /opt/customer-lsap
```

During `install`, `lsapctl` syncs the extracted package directory into `installDir` before installing systemd units. Later lifecycle commands should be run from the installed directory or with `--manifest <installDir>/rendered/lsapctl-runtime.json`.

If the target install directory already exists and is not empty, `lsapctl install` warns and asks for confirmation before continuing. With `--yes`, it continues and still performs the configured backup unless `--no-backup` is set.

Backup behavior:

```bash
./lsapctl install --backup-dir /data/package-backups
./lsapctl install --no-backup
```

By default, if `installDir` already exists, `lsapctl install` copies it to:

```text
<parent>/.lsapctl-backups/<installDirName>-YYYYMMDD-HHMMSS
```

The current implementation lives in:

```text
lsapctl/
```

Build for Linux:

```bash
cd lsapctl
GOOS=linux GOARCH=amd64 go build -o ../dist/lsapctl .
```

During packaging, `LSAPCTL_BUILD_CMD` should place the binary at the package context root:

```bash
LSAPCTL_SOURCE_DIR=/path/to/packaging-platform/lsapctl
DAGGER_LINUX_BASE_IMAGE=golang:1.25-alpine
LSAPCTL_BUILD_CMD='cd /workspace/context/lsapctl-src && GOOS=linux GOARCH=amd64 go build -o "$OUTPUT_DIR/lsapctl" .'
```

The generated package should contain:

```text
lsapctl
rendered/lsapctl-runtime.json
```

## Runtime Manifest

`rendered/lsapctl-runtime.json` is generated by Dagger.

```json
{
  "schemaVersion": "lsapctl.runtime/v1",
  "productId": "lsap",
  "version": "latest",
  "installDir": "/opt/lsap",
  "files": {
    "compose": "rendered/docker-compose.yml",
    "systemdDir": "systemd",
    "config": "rendered/install-config.json",
    "buildLock": "rendered/build-lock.json",
    "workloads": "rendered/workloads.json"
  },
  "workloads": [
    {
      "id": "location-guard",
      "runtime": "docker",
      "composeService": "location-guard"
    },
    {
      "id": "location-worker",
      "runtime": "systemd",
      "unitName": "lsap-location-worker.service"
    }
  ]
}
```

## Docker Workloads

`lsapctl` should manage Docker workloads through Docker Compose.

Required behavior:

- detect `docker compose` first, then fallback to `docker-compose`
- run `compose up -d` for docker workloads during `start`
- run `compose down` or service-level stop during `stop`
- include compose service status in `status`
- validate that Docker daemon is reachable before install/start/status

## systemd Workloads

`lsapctl` should manage systemd workloads from `systemd/*.service`.

Required behavior:

- install unit files into `/etc/systemd/system`
- run `systemctl daemon-reload`
- run `systemctl enable <unit>` during install
- run `systemctl start/stop/status <unit>` for lifecycle commands
- run `systemctl disable --now <unit>` and remove unit files during uninstall

## CentOS Support

CentOS is supported with these assumptions:

- CentOS 7, 8, Stream 8, Stream 9, Rocky Linux, AlmaLinux
- systemd is present
- Docker Engine or a compatible Docker CLI is installed when Docker workloads are enabled
- `docker compose` plugin is preferred; legacy `docker-compose` is accepted

`lsapctl doctor` should detect OS details from:

```text
/etc/os-release
```

Minimum checks for CentOS-like distributions:

- `ID` in `centos`, `rhel`, `rocky`, `almalinux`
- `VERSION_ID` is supported by policy
- `systemctl` exists and systemd is PID 1, or systemd commands are usable
- SELinux status is reported when `getenforce` exists
- firewalld status is reported when `firewall-cmd` exists

CentOS-specific notes:

- CentOS 7 often has older Docker Compose packaging. Prefer bundling/declaring the Compose plugin requirement.
- If SELinux is enforcing, `lsapctl doctor` should warn when install paths or bind mounts need labels.
- If services need privileged ports or firewall openings, `lsapctl doctor` should report required changes before install.

## Privilege and Permission Model

`lsapctl` does not require every command to be started with `sudo`.

Commands that can usually run without root:

- `doctor` - reads environment state and reports missing permissions as checks.
- `status` - can run without root when `systemctl status` and Docker are readable by the current user.
- `completion` and `help` - never require root unless writing completion files into a system directory.

Commands that require root or equivalent privileges:

- `install` - writes the install directory, installs systemd unit files, and runs `systemctl daemon-reload`.
- `uninstall` - disables/removes systemd unit files and reloads systemd.
- `start`, `stop`, and `restart` - require root when any selected workload uses `systemd`.

Docker-only `start`, `stop`, `restart`, and `status` do not force root. They require access to the Docker daemon, which usually means one of:

- run through `sudo`
- run as root
- add the user to the Docker group according to the host policy

Root is detected with:

```text
effective uid == 0
```

The CLI supports dynamic privilege elevation on Linux. For commands that require root, if the current process is not root and `sudo` exists, `lsapctl` asks whether it should re-execute itself through `sudo`.

Examples:

```bash
./lsapctl install
./lsapctl restart --workload location-worker
```

If either command needs root, `lsapctl` prompts:

```text
install requires root privileges. Re-run with sudo?
```

For unattended installs, `--yes` allows automatic sudo re-exec without the confirmation prompt:

```bash
./lsapctl install --yes
```

For environments where auto-elevation is not allowed, use `--no-elevate`. In that mode, `lsapctl` exits with a clear error and the caller can decide whether to run `sudo ./lsapctl ...`.

```bash
./lsapctl install --no-elevate
```

Before lifecycle commands:

- root is recommended for systemd operations
- non-root status may be allowed only if Docker/systemd commands are readable
- if Docker workloads exist, current user must be root or in the Docker group

Required path checks:

- install directory parent exists or can be created
- install directory is writable during install
- config files are readable
- component files are readable
- systemd directory is readable
- `/etc/systemd/system` is writable during install/uninstall
- Docker socket is reachable when Docker workloads exist

## Environment Checks

`doctor` should return a structured result and non-zero exit code on blocking failures.

Recommended checks:

- OS family and version
- CPU architecture
- free disk space for install directory
- required ports availability
- required commands:
  - `systemctl` for systemd workloads
  - `docker` for docker workloads
  - `docker compose` or `docker-compose` for docker workloads
- Docker daemon connectivity
- systemd availability
- SELinux mode
- firewall service state
- existing service name conflicts
- existing container name conflicts
- existing install directory conflicts

Recommended severity:

- `error` - install/start should stop
- `warning` - operation can continue but needs attention
- `info` - diagnostic context

Example:

```json
{
  "ok": false,
  "checks": [
    {
      "id": "permission.root",
      "severity": "error",
      "message": "install requires root"
    },
    {
      "id": "docker.daemon",
      "severity": "error",
      "message": "Docker daemon is not reachable"
    },
    {
      "id": "selinux.mode",
      "severity": "warning",
      "message": "SELinux is enforcing; bind mount labels may be required"
    }
  ]
}
```

## Packaging Contract

The package must include `lsapctl` at the package root or in a documented bin path.

Recommended layout:

```text
lsapctl
rendered/lsapctl-runtime.json
rendered/docker-compose.yml
rendered/install-config.json
systemd/*.service
components/*
```

Users should run:

```bash
./lsapctl doctor --manifest rendered/lsapctl-runtime.json
./lsapctl install --manifest rendered/lsapctl-runtime.json
./lsapctl start --manifest rendered/lsapctl-runtime.json
```

For non-interactive provisioning:

```bash
./lsapctl install --yes --manifest rendered/lsapctl-runtime.json
./lsapctl start --yes --manifest rendered/lsapctl-runtime.json
```
